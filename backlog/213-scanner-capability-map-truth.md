# 213 — Scanner capability map: `ScannerPort::applies_to`, adapter-owned truth, evidence per cell

**Issue:** #259 (item 1 of 2) · **Branch:** `agent/259-scan-capability-map`
**Governing decisions:** ADR 0015 (a field accepted at apply must be load-bearing at runtime or rejected at apply), ADR 0007 (an unassessed surface fails closed; the absence of a surface does not hold), ADR 0005 (format capability taxonomy — the format axis of the map is the compiled-in handler key), ADR 0056 (payload SBOMs — what `osv` consumes). No new ADR: this item applies 0015 to the scan axis exactly as the provenance axis already does.

## Why

The provenance axis has a static backend→format capability map and a fail-closed apply-time linter (`StaticConfigValidator` row 7, `provenance_capable_formats`, Tier 1 = `{"oci"}`; the adapters own the truth via `ProvenancePort::applies_to`). The scan axis has nothing comparable: a `ScanPolicy` that points a backend at a format it cannot serve is accepted at apply and does nothing at runtime — the anti-pattern shape CLAUDE.md names. Known inert pairings today: `osv × oci` (OCI has no SBOM source; the OSV adapter answers a missing SBOM with an **empty clean verdict**, so on an OCI repository `osv` is a false release authority whenever `trivy` abstains), and every backend on a format no compiled-in handler serves (`gradle`, `generic`, …: kind `Other`).

This item establishes the **truth**: what each backend can analyse per format, owned by the adapter, mirrored by one static record in `hort-app` (the apply path has no adapters), guarded for parity, and **proven per cell by a test on a known-vulnerable fixture**. Item 214 wires the consumers (apply-time linter, orchestrator, docs).

## The map — rule and cells

**Rule (binding):** a cell is "yes" only if a test exists in which a known-vulnerable fixture of that format, materialised by that backend, yields **≥ 1 finding**. No test ⇒ "no". The map is binary in code; what a "yes" covers (own identity vs. declared dependencies, which kinds) is described per cell in the docs table (item 214) — not encoded as a third state, because every non-OCI Trivy cell is partial in some way and a "partial" warning on every policy would be noise.

| backend | oci | maven | pypi | npm | cargo | any other format key |
|---|---|---|---|---|---|---|
| `trivy` | **yes** — `an_oci_layer_with_an_os_package_database_yields_findings` | **yes** — `a_known_vulnerable_jar_yields_its_cve`, `a_pom_is_analysed_rather_than_ignored` | **yes** — `a_known_vulnerable_wheel_yields_at_least_one_finding` | **yes** — NEW test (below); staging proof exists (`lodash-4.17.20.tgz` → 5 own-identity findings) | **yes iff** the NEW `Cargo.lock` test passes (below); otherwise **no** | no |
| `osv` | **no** (no SBOM source for OCI) | **yes** — `dogfood/maven-osv-scan` (hosted + proxy legs, `spring-web` → finding on `spring-beans`), staging proof 24 findings | **yes** — pypi `PayloadSbom` | **yes** — npm SBOM (`event-stream@3.3.6` alpha runbook) | **yes** — cargo `PayloadSbom` (`hort-crates` staging) | no |

For `osv`, "yes" ⇔ the format's compiled-in handler exposes an SBOM the orchestrator's `try_extract_sbom` can use (`payload_sbom().is_some()` or a metadata `extract_sbom`) — derive the list from that, do not hand-maintain a second one. If a unit-level "known-vulnerable SBOM ⇒ ≥ 1 finding" test does not already exist in `hort-adapters-scanner-osv` (check `tests/`), add one per the rule (an OSV-scanner-gated test in the shape of the Trivy evidence file is acceptable; it self-skips without the binary exactly like `TRIVY_BIN`).

## What to build

1. **Port.** `ScannerPort::applies_to(&self, format: &str) -> bool` in `crates/hort-domain/src/ports/scanner.rs`, required (no default), documented as the mirror of `ProvenancePort::applies_to` (`crates/hort-domain/src/ports/provenance.rs:259-269`): "whether this backend can produce a verdict for at least one artifact kind of the format; the orchestrator does not invoke a backend on a format it does not apply to". Update every impl and mock (`scan_orchestration_tests.rs:210`, `hort-worker/src/composition.rs:2460`).
2. **Trivy truth.** `TrivyAdapter::applies_to` returns true for exactly the formats whose kinds have a materialisation `Plan` other than `NotApplicable` (`workspace.rs::plan_of`) **and** carry a passing evidence test. Add a unit test pinning the set. The format→kinds association: read the handlers' `scan_kind` impls (`hort-formats/src/{oci,npm,cargo,pypi}.rs`, `maven/mod.rs`); the adapter itself sees only the format string, so the list is static in the adapter and pinned by the parity guard (5).
3. **OSV truth + F3 fix.** `OsvScannerAdapter::applies_to` = the SBOM-capable formats (static in the adapter, guarded in 5). **Fix the no-SBOM branch** (`hort-adapters-scanner-osv/src/lib.rs:429-435`): `sbom: None` must return `Ok(ScanAnalysis::NothingAnalysable(NotAnalysable::NotApplicable))`, never `ScanAnalysis::clean()`. `NotApplicable` (non-gating) is correct: a missing SBOM is a fact about the artifact (an OCI blob, a checksum sidecar, a `-sources.jar` — kinds the handler declares to carry no dependency information), the same arm Trivy uses for a manifest row; the partition in `run_scan` then does the right thing in every combination (Trivy analysed ⇒ Trivy's verdict; Trivy `NotApplicable` too ⇒ completed `not_applicable` assessment; Trivy gating ⇒ hold). Log at `debug!` (the steady-state, per the orchestrator's own level rule at `scan_orchestration.rs:483-495`). Update `scan_with_none_sbom_returns_empty_findings_without_invoking_cli` to assert the new shape; add the orchestrator-level test that a `[trivy, osv]` policy on an OCI layer where Trivy abstains `NotApplicable` records `ScanAssessment::NotApplicable` and **not** a clean `ScanCompleted` (the F3 false-authority case, closed).
4. **Static record in `hort-app`.** In `crates/hort-app/src/scanning.rs` (already the scan-axis analogue of `provenance.rs`): `pub fn scan_backend_applies_to(backend: &str, format: &str) -> bool` as an exhaustive match over the backend names, plus `pub fn any_scan_backend_applies_to(format: &str) -> bool`. `KNOWN_SCAN_BACKENDS` stays the single record of the backend set — the map's rows **are** that const (a test: every backend in `KNOWN_SCAN_BACKENDS` has ≥ 1 "yes" format; an unknown backend is false for every format). Module docs: the rule above, and why the record is static (same reason as `KNOWN_SCAN_BACKENDS`: the apply path runs in the server, which has no scanner adapters; H20).
5. **Parity guard** in `crates/hort-worker` (the one crate that constructs the real adapters **and** the handler registry, `composition.rs:398-490`): a test asserting, for every registered handler key × every `KNOWN_SCAN_BACKENDS` name, `adapter.applies_to(key) == hort_app::scanning::scan_backend_applies_to(name, key)`; and, for `osv`, that `applies_to(key)` equals the handler's SBOM capability (`payload_sbom().is_some()` / metadata extract). Construct the adapters without I/O (`TrivyAdapter::new(cfg, storage)` with a mock storage; `OsvScannerAdapter::new(cfg)`) — no health check, no binary. Comment states the invariant: "the apply-time linter reads the static record; the worker dispatches on the adapter's answer; they must never disagree".
6. **Evidence tests (rule enforcement)** in `crates/hort-adapters-scanner-trivy/tests/materialisation_evidence.rs`:
   - `a_known_vulnerable_npm_tarball_yields_its_own_advisory`: tarball with `package/package.json` = `{"name":"lodash","version":"4.17.20"}` (+ a stub `index.js`), kind `NpmTarball`, coords name `lodash` 4.17.20. Expect ≥ 1 finding attributed to `lodash@4.17.20` (CVE-2021-23337 / CVE-2020-28500 era). Keep the existing "nothing to attribute" test — it pins the *other* half (no dependency advisories from ranges).
   - `a_binary_crate_with_a_lockfile_yields_a_dependency_advisory`: `.crate` with `Cargo.toml` (`[package] name="evidence" version="1.0.0"`, `[dependencies] smallvec = "1"`) **and** `Cargo.lock` (v3 format) pinning `smallvec 1.6.0` (RUSTSEC-2021-0003 / CVE-2021-25900). Trivy's Cargo analyzer reads `Cargo.lock` in `fs` mode (coverage matrix: `Cargo.lock` — all targets). Expect ≥ 1 finding. **If this test cannot be made to pass** with a correct fixture (state what Trivy reported), the `trivy × cargo` cell is **no** — set it so in (2)/(4) and say so in the report; item 214 then adjusts the in-repo fixtures that pair trivy with cargo.
   Both are `TRIVY_BIN`-gated like their siblings. Run them in the sandbox with the Trivy binary if available (`command -v trivy`; otherwise say so — do not report a self-skipped test as proof).
7. **Glossary:** `docs/glossary.md` entry **scanner capability map** (the static backend→format record; a cell is "yes" only with a known-vulnerable-fixture test; mirrors the provenance capability set).

## Not in this item

No linter change, no orchestrator change, no docs table, no fixture sweep (all item 214). No new policy option, no opt-out, no change to verdict/gate semantics beyond the F3 fix. `KNOWN_SCAN_BACKENDS` is not renamed.

## Acceptance

- `ScannerPort::applies_to` exists; both adapters implement it from their own materialisation/SBOM truth; the `hort-app` static record matches them by construction (parity guard green).
- Every "yes" cell names a passing known-vulnerable-fixture test; the two new Trivy tests exist and the report states whether they ran (binary present) or self-skipped.
- `osv` with `sbom: None` returns `NothingAnalysable(NotApplicable)`; the orchestrator test proves a Trivy-abstains + osv-no-SBOM OCI layer records `not_applicable`, not clean.
- Gate green: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo-audit audit --deny warnings`, `cargo deny check`. Code comments state invariants, never issue numbers.
