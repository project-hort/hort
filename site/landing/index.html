Core principles

Built around verifiable artifacts.

Artifact infrastructure should make it possible to understand what was stored, where it came from, and what happened before it became available.

Content-addressed storage

SHA-256-based content addressing links stored artifacts to their digests.

Verified upstreams

Checksum verification is part of retrieving artifacts from upstream repositories.

Controlled release

Quarantine and scanning workflows support explicit release decisions.

Traceable events

Event-based auditing supports a verifiable record of artifact operations.

Built for operations

Compact deployment. Independent workers. Observable, validated configuration.

Deploy a compact API server, scale background processing separately, and manage configuration in version control.

Git-friendly

File-based configuration

Keep configuration files in Git, review changes in pull requests, and manage configuration alongside your infrastructure code.

Scale separately

Independent workers

Scanning and background tasks run in separate worker processes, independently of the API server. Allocate CPU and memory where they're needed, and scale workers separately in containerized and cloud deployments.

Validate · Observe

Ready for AI-assisted operations

Version-controlled configuration, an offline validation command, and rich operational metrics provide inputs for AI-assisted review, troubleshooting, and automation. hort does not require or include an AI agent.

Identity & access

Identity establishes who you are. Grants determine what you can do.

hort distinguishes enterprise user authentication from workload federation. Both paths lead to repository authorization, but they use different identity and permission mechanisms.

01 · Human access

Enterprise OIDC

Enterprise IdPOIDC access token validationClaim mappings → RBAC claimsRepository authorization

Claim mappings derive authorization-relevant claims for human users. A valid token alone does not grant access to every repository.

02 · Workload access

Pipeline OIDC federation

CI/CD OIDC tokenIssuer + federated identity claim matching/api/v1/auth/exchangeShort-lived service-account tokenPermission grants + token scope capRepository authorization

Federated workloads use configured service-account identities and explicit permission grants, not human-user claim mappings.

Authentication ≠ authorizationRepository operations are checked against the applicable permissions.

Configuration as code

Your artifact infrastructure, defined in files.

Store repository and access configuration in version-controlled YAML. Run `hort-server validate-config --strict` before deployment; hort then applies the validated desired state at server startup. No continuous reconciliation is implied.

A real repository configuration

Excerpt from deploy/ansible/files/gitops/repositories/dockerhub-proxy.yaml. This is an actual project example, shortened for readability.

ARTIFACT REPOSITORY · YAML
apiVersion: project-hort.de/v1
kind: ArtifactRepository
metadata:
  name: dockerhub-proxy
spec:
  name: "Docker Hub pull-through (hardened)"
  format: oci
  type: proxy
  storage:
    backend: filesystem
    path: /var/lib/hort-server/cas/dockerhub-proxy
  proxy:
    upstreamUrl: "https://registry-1.docker.io"
  isPublic: false

Getting started

Your server or your cluster.

Run hort as a native executable on a host or deploy it to Kubernetes. Choose the operational model that fits your infrastructure.

The hort CLI is an operator tool for managing and interacting with hort. It belongs alongside native and Kubernetes deployment workflows, not in a separate product category. Get release binaries

01 · Native

Run the executable directly.

Deploy hort on a Linux server or virtual machine without requiring Kubernetes. Manage the process and configuration using your existing host automation.

The repository includes an Ansible deployment example. Treat it as a starting point for your own environment, not a mandatory installer.

Explore the Ansible example
02 · Kubernetes

Deploy with Helm.

Use the documented Helm chart and an environment-specific values file for a Kubernetes deployment.

helm install hort oci://registry.hort.rs/hort-charts/hort-server \
  -f my-values.yaml
Read Helm chart documentation

Both paths require environment-specific configuration and prerequisites. Exact native startup commands, chart settings and health checks should be taken from the corresponding release documentation.
